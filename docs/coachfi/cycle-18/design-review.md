# C18 — przegląd projektu zapisu Review

Przed implementacją niezależnie odczytano dotychczasowy ReviewPage, createQuizSaveController, rzeczywisty recordAnswer, ProductStorage oraz callback markActive ze StreakContext. Obserwacje actual UI/data należą do osobnych recenzentów; nie powtarzano ich testów. Ten dokument jest oceną projektu i granic, a nie przyjęciem aplikacji lub własnego helpera.

Dotychczasowy kontroler quizu blokuje powtórne wejście i własny zakończony ticket. Jego reset usuwa jednak również quarantine. Samo przeniesienie wzorca QuizCard do Review nie wystarczy: zmiana języka, restart, Next lub synchroniczny event podczas zapisu mogłyby unieważnić stary wynik i jednocześnie otworzyć nową próbę nad częściowo zmienionymi danymi.

Uzgodniony nowy adapter Review tworzy osobny istniejący delegate dla każdego ticketu i nigdy go nie resetuje. begin/retire zamykają wyłącznie kontekst widoku. Osobna blokada inFlight obejmuje bieżący kontroler i zakres owner+revision; nie pozwala zagnieżdżonemu nowemu ticketowi lub kontrolerowi uruchomić drugiego zapisu. Sticky uncertainty pozostaje we wspólnym RAM modułu dla semantycznego właściciela i rewizji przez zmianę handle, języka, pytania, sesji i remount. Do 64 zakresów zachowujemy blokadę bez wyrzucania wcześniejszych; przekroczenie pojemności blokuje kolejne operacje w RAM.

Fenced storage sprawdza ticket i uchwycony handle przed oraz po odczycie/zapisie. Każda próba set/remove jest oznaczona przed walidacją i delegacją. Jeżeli kontekst zmieni się po próbie mutacji, nie wolno pokazać sukcesu starego widoku. Przy nadal bieżącym właścicielu wynik jest uncertain; po utracie właściciela stopped, a stary zakres pozostaje zablokowany. Błąd przed mutacją pozwala wyłącznie na świadomą próbę tego samego ticketu; stary widok jest inertny.

Callback streak działa wewnątrz delegate, po SRS i przed zwróceniem saved. Jego błąd lub wynik asynchroniczny oznacza uncertainty. Dopiero po saved strona ma wycofać stary ticket przed opublikowaniem results/revealed. Next, restart i wybór odpowiedzi wymagają bieżącego kontekstu oraz właściwego stanu odpowiedzi. Stare Next/restart i opóźniony confetti timeout nie mogą zmieniać nowej sesji. Po stale wyniku uncertain strona nie publikuje starego feedbacku, ale odświeża alert dla nadal tego samego owner+revision.

Actual finding C18-DATA-01 wykazał, że getAllCards po błędzie parse zwraca pustą listę, a następnie rzeczywisty recordAnswer ją zapisuje. W nowym adapterze readReviewCards odmawia odczytu nieznanych bajtów zamiast traktować je jako pusty deck. Każdy fenced odczyt SRS ponawia walidację, także wewnątrz recordAnswer. Null oznacza brak kart; pozostałe dane wymagają tablicy, unikalnych niepustych własnych ID, bezpiecznych nieujemnych całkowitych interval/repetitions, skończonego easeFactor co najmniej 1.3 i prawdziwej daty YYYY-MM-DD. Zachowujemy nieznane ID i dodatkowe pola. Historyczne interval 131/393 są poprawne: limit 90 należy do nowego wyniku istniejącego calculateNext. Pierwotne wymaganie odczytu 0..90 skorygowano po niezależnym przeglądzie źródła przed pierwszym uruchomieniem. Nie jest to migracja.

Adapter potwierdza dokładny raw SRS po setterze i ponownie po callbacku activity. Nie oznacza to atomowej transakcji lub potwierdzenia chmury. markActive może częściowo zapisać streak/bonus przed błędem; nie cofamy danych i nie naliczamy bezpośrednio nagrody pytania w Review. RAM nie daje exactly-once po przeładowaniu lub w innych kartach. Odmowa i no-op zachowują surowe bajty; poprawny rzeczywisty zapis może normalnie serializować JSON.
