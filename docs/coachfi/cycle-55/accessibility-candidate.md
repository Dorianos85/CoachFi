# C55 — kandydat B07: pierwszy onboarding osoby dorosłej

Status: **STATIC_CANDIDATE_PENDING_BASELINE**, 18.10.2026. Tylko odczyt źródeł oraz ten raport i JSON. Nie wykonano produktu, testów, kompilatora, buildu ani przeglądarki; nie jest to finding z Chrome, przyjęcie poprawki lub WCAG PASS. C54 fixtures pozostają zamrożone. Nie zmieniono rejestrów programu.

Kandydat jest uzasadniony w rzeczywistej ścieżce, a nie przez pominięcie wrappera. `AppNavigation.tsx:679` renderuje `OnboardingModal` bez nadrzędnego Dialog. Sąsiedni `ModeGate` jest oddzielnym komponentem i otrzymuje własny `returnFocusRef`. Wspólny `ui/dialog.tsx` opakowuje istniejący Radix Dialog, lecz OnboardingModal go nie importuje ani nie używa. `ProductScopeBoundary`, Providers i layout nie dodają tej instancji mechanizmu modalnego. W lokalnie zainstalowanym Radix 1.3.1 widać FocusScope/loop/trapFocus, ale ta ścieżka nie jest do niego podłączona.

Sprawdzone w źródłach:

- `OnboardingModal.tsx:65` ma `role="dialog"` i `aria-modal="true"`, ale nie ma `aria-label`/`aria-labelledby` ani `title`. Widoczne tytuły obu kroków są zwykłymi `p` bez ID i powiązania z dialogiem (`:92`, `:115`). To potwierdzona luka deklaracji nazwy; obliczonego drzewa dostępności nie oglądano.
- Pole imienia (`:94`) ma `autoFocus`, placeholder PL/EN, limit32 oraz Enter→następny krok. Nie ma powiązanego `label`, ID lub nazwy ARIA. **Nie twierdzimy, że jego computed accessible name jest pusty**: placeholder może być fallbackiem. Potwierdzony jest brak trwałej, powiązanej etykiety.
- W tej instancji nie ma kodu ograniczającego Tab/Shift+Tab, inert tła, obsługi Escape lub powrotu focusu. Ciemny overlay i `aria-modal` deklarują modalność, ale źródło nie podłącza zachowania wrappera. Uciekanie focusu jest prawdopodobnym skutkiem do sprawdzenia, nie wynikiem testu.
- Początkowy focus nie jest całkiem pominięty: istnieje `autoFocus` inputa. Krok2 usuwa input i nie wskazuje nowego celu focusu. Rzeczywisty focus po animacji oraz po zamknięciu nadal wymaga obserwacji w przeglądarce.

Wzorzec [WAI APG Dialog (Modal)](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) opisuje nazwę dialogu, focus wewnątrz, zamkniętą sekwencję Tab, Escape i sensowny cel po zamknięciu. [WAI Labeling Controls](https://www.w3.org/WAI/tutorials/forms/labels/) opisuje powiązanie etykiety z polem. To odniesienia projektowe, nie pełna ocena zgodności. Sprawdzone18.10.2026.

Warunki wejścia i zapisu są już istotne dla lokalnej poprawki. Caller włącza onboarding dopiero po wymaganych zgodach, załadowanym adult mode; komponent sprawdza aktualny owner i `getUser(storage).setupDone`. `useProductStorage` przechwytuje handle właściciela, a boundary remountuje treść przy zmianie revision. Next kroku1 nie zapisuje; zakończenie zapisuje przycięte imię/cel/setupDone, a „Pomiń na razie” zapisuje pusty profil/setupDone. Oba handlery sprawdzają owner przed i po `saveUser`; wyjątek pokazuje alert i zachowuje dialog. `saveUser` wykonuje istniejący lokalny zapis profilu, downstream notify i event. Ten przegląd nie potwierdza chmury ani kompletności gwarancji zapisu.

Istniejące testy nie zamykają tego kandydata. W przeszukanych `tests` i testach `app/components/lib` nie znaleziono bezpośredniego testu OnboardingModal. `p0-safety.spec.ts:33` sprawdza focus/Escape **ModeGate**, przy profilu `setupDone:true`; `core-loop.spec.ts:7` jawnie omija onboarding takim profilem. Testy cloud z `onboarding_done` nie są testami tego dialogu. Nie uruchamiano ich ponownie.

Minimalny plan przed ewentualną zmianą: dwie nowe gałęzie Chrome w PL/EN na realnym shellu i realnym wrapperze, PL→zakończenie i EN→skip; to nie pełna macierz2×2. Świeże puste konteksty, syntetyczny guest i profil bez setupDone, opcjonalne funkcje false, API i zewnętrzne żądania zablokowane. PL przechodzi istniejące required-consent i adult gate klawiaturą, aby zobaczyć prawdziwe przekazanie focusu do onboardingu; EN ma już syntetycznie ustawione wymagane zgody/adult, aby izolować ten jeden dialog. Poprzednie bramki są setupem PL, nie nowym audytem ich dostępności. Obserwować oba kroki: nazwę dialogu, trwałą nazwę pola po wpisaniu, początkowy focus i jego zmianę po Enter, zawijanie Tab/Shift+Tab na granicach, brak wejścia w tło, Escape, połączenie celu focusu po zamknięciu, klawiaturowe zakończenie/skip oraz reload. Zebrać obserwacje niezależnie przed asercjami, aby pierwsza brakująca nazwa nie ukryła pozostałych danych. Rzeczywisty baseline dopiero rozstrzygnie które oracles zawodzą; autoFocus jest pozytywną kontrolą.

Przed zamrożeniem future fixtures root powinien ustalić lokalny kontrakt Escape i logiczny cel dla automatycznego otwarcia bez triggera. Propozycja: Escape zamyka stan bez zapisu, dzięki czemu nie staje się ukrytym `handleSkip` i nie dopisuje setupDone; jawne finish/skip zachowują swoje obecne zapisy. To propozycja do peer, nie już zatwierdzony zakres. Sprawdzić przekazanie focusu z zamykanego ModeGate w gałęzi PL; gałąź EN z zasianym adult sama tego przejścia nie dowodzi. Każde przyszłe spięcie close/save musi zachować alert przy odmowie zapisu, aktualność owner i brak zapisu do późniejszego właściciela.

125punktów i istniejące postępy mają pozostać byte-for-byte; przed jawnym finish/skip brak zapisu profilu. Po sukcesie tylko oczekiwany profil, bez usunięć; reload nie otwiera ukończonego onboardingu. W razie Escape bez zapisu reload może pokazać go ponownie. Odczytów/zapisów realnych danych nie planujemy. Użycie istniejącego Radix może być najmniejszą lokalną opcją, ale nie wolno bez kontroli dodać domyślnego Close zapisującego profil ani mockować wrappera w testach focusu.

Czytnik ekranu, pełne WCAG2.2AA, inne dialogi/locale, real auth, cloud, Kids i voice pozostają poza tym kandydatem. Nowe dane onboardingu, zmiana rynku lub obowiązkowości potwierdzenia wieku wymagałyby odrębnego zakresu; niczego takiego nie proponowano ani nie eskalowano. AI/cloud writes HARD_OFF, produkcja NO-GO.
