# Niezależna recenzja bezpieczeństwa kodu CoachFi

14 października 2026. Recenzent: `/root/ux_audit`, rola 14/4 w drugiej fali, niezależny od autora źródłowego kodu. Scope: lokalny `source/CoachFi`, commit `86226ddc2c672b3d3d88869ebd8c5f6a5a59c19b`; auth, API, zgody, Supabase, migracje, AI i limity. Recenzja nie zatwierdza własnego raportu UX.

**Decyzja dla przyjmowania użytkowników: no-go do zamknięcia wysokich ryzyk i zebrania dowodów staging.** Potwierdzono w kodzie otwarte ścieżki zapisu/użycia dostawców oraz obecność pakietów objętych critical advisories. Metadane Vercel A24/A25 powiązały badany commit z READY production deployment `dpl_AaEiWV85rietTuq3Z5GqogCu3DuN`, aliasem coachfiai.com i ID widocznym w assetach publicznego DOM. Nie przeprowadzono exploita produkcji ani nie odczytano potencjalnie wrażliwych baz profilu przeglądarki. [Dowód metadanych](../../../evidence/architecture.json).

## Metoda i ograniczenia

Odczyt kodu i SQL, `git ls-files`, lockfile, lokalne `npm explain shell-quote` oraz trzy lokalne testy dokładnych funkcji `api-security.ts` po usunięciu adnotacji TypeScript. Testy nie wykonywały sieci, zapisu w aplikacyjnej bazie ani wywołania AI. Dowody: [security-code-review.json](../../../evidence/security-code-review.json). Zespół oddzielnie dostarczył [npm-audit.json](../../../evidence/npm-audit.json): 42 wpisy pakietów (20 moderate, 20 high, 2 critical), **nie 42 niezależne exploity**. Typecheck, 50 testów jednostkowych i build przeszły według dowodów koordynatora; ich pass nie dowodzi autoryzacji, zgodności zgód czy braku podatności zależności.

Nie uruchamiano obcego AI, mikrofonu, kont dostawców, migracji, walletu, mintowania, zmian repo zdalnego ani testów zakłócających. Nie odczytywano zawartości `Cookies`, `Login Data`, `History`, lokalnych baz profilu ani sekretów. Konfiguracja aktywnej bazy/hostingu, polityki reverse proxy, regiony/retencja dostawców i pełny staging pozostają niesprawdzone.

## Granice zaufania

Aktywa: tożsamość konta i postęp, ewentualny profil/kwoty finansowe, zgody, integralność rankingu i dowodów ukończenia, klucze server-only, środki/limity dostawców AI/głosu oraz dane środowiska developerskiego.

Granice: przeglądarka i localStorage → własne API → Coinbase CDP/Supabase service role → Anthropic/OpenRouter/ElevenLabs/Solana; osobno historia Git i artefakty CI. Dane klienta, deklarowany nagłówek zgody, IP z nagłówka oraz nazwa/score/certificate z payloadu nie są samodzielnym dowodem uprawnień, zgody ani osiągnięcia.

### SEC-10 — medium: eksport może zawierać materiał sesji

`DataSafetyPanel.tsx` kolekcjonuje wszystkie klucze zaczynające się od `coachfi-`, z localStorage i sessionStorage, i zapisuje ich surowe wartości do eksportu. Supabase browser client ustawia storageKey `coachfi-auth`. Gdy ta ścieżka ma zapisaną sesję, eksport może zawierać jej access/refresh tokeny. Potwierdzono zakres funkcji i syntetyczny test klucza; nie pobrano realnego eksportu i nie odczytano tokenów użytkownika. Skutek ujawnienia wymaga przekazania pliku komuś innemu lub kompromitacji miejsca jego zapisu — nie jest to samodzielny zdalny exploit.

Poprawka: allowlista danych eksportowalnych, jawne wykluczenie danych uwierzytelnienia/SDK oraz test „syntetyczne coachfi-auth nie trafia do pliku”. Usuwanie oznaczone jako lokalne nie jest samo w sobie błędem; pełny proces praw danych musi osobno obejmować konto i dostawców. Właściciel 12/15, recenzent 14. Źródła: [DataSafetyPanel](../../../components/DataSafetyPanel.tsx), [Supabase client](../../../lib/supabase/client.ts).

## Sprawdzone pozytywne elementy i wymagające dalszych testów

- `/api/account` pobiera user ID z `verifyCdpUser`, delegującego do `cdp.endUser.validateAccessToken`; klient nie wybiera ID cudzej osoby. CRUD używa tego ID. To pozytywny wzorzec statyczny, bez dowodu testu dwóch kont.
- Migracje accounts/account_state/progress/certificates włączają RLS i nie dodają anon/authenticated policy dla prywatnych kont; API używa server-only service role. Sama RLS nie chroni zapisów wykonywanych przez service role, dlatego ważna jest poprawna autoryzacja API. [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).
- Starszy `supabase/schema.sql` ma własnościowe polityki auth.uid(), view reward_balances z `security_invoker=true`, a funkcja SECURITY DEFINER mark_active_today sprawdza uid i ma revoke PUBLIC. Nie zgłaszamy samego SECURITY DEFINER ani view jako wykrytej luki. Są jednak dwie ścieżki tożsamości/SQL (Supabase UUID oraz CDP text ID), m.in. różne definicje certificates; migracja fresh i upgrade oraz katalog faktycznej bazy wymagają sprawdzenia.
- Są limity rozmiarów wiadomości/historii/odpowiedzi, sanitizacja displayName, fallback chat i timeouty TTS/Mila. Nie stanowią globalnego limitu kosztów ani oceny merytorycznej AI.
- Next config deklaruje CSP, frame-ancestors none, nosniff i Permissions-Policy. CSP nadal dopuszcza unsafe-inline/unsafe-eval; nie znaleziono bezpośrednio exploitable XSS w tym przeglądzie. Nagłówki faktycznego deploymentu i reachability Supabase browser API wymagają testu. Nie ogłaszamy odporności XSS.
- Nie potwierdzono wycieku klucza service role w klientowych importach; ograniczona kontrola nie jest pełnym secret scanem historii i artefaktów. Profile repo pozostają priorytetem SEC-01.

## Mapa standardów i bramka retestu

Odczytano [ASVS 5.0.0](https://owasp.org/projects/asvs), oficjalny katalog 5.0 XML oraz [LLM10:2025 Unbounded Consumption](https://genai.owasp.org/llmrisk/llm102025-unbounded-consumption/). Wersjonowane wymagania użyte częściowo: ASVS **v5.0.0-4.1.3** (zaufanie do nagłówków proxy — SEC-07, dynamicznie pending), **v5.0.0-14.2.4** (kontrole ochrony danych — SEC-01/05), **v5.0.0-14.3.1** (czyszczenie client storage po końcu sesji — pending), **v5.0.0-15.1.3** (dokumentowanie funkcji kosztownych — SEC-03/07). To mapowanie zakresu, nie certyfikacja spełnienia. Pełne wymagania autoryzacji/OAuth mają zostać przypisane po ustaleniu finalnego modelu kont i stagingu; nie dopisano wymyślonych IDs.

Źródło katalogu wymagań: [oficjalny ASVS 5.0 XML](https://github.com/OWASP/ASVS/blob/master/5.0/docs_en/OWASP_Application_Security_Verification_Standard_5.0.0_en.xml). Supabase changelog Markdown nie był dostępny przez parser narzędzia; sprawdzono [oficjalne breaking changes](https://supabase.com/changelog?types=breaking-change). Nie wykonywano implementacji/migracji, więc nie rozstrzygnięto wszystkich zmian zależnych od aktywnej wersji bazy.

Kolejność: (1) klasyfikacja profili i ograniczenie ryzyka incydentu, (2) dependency triage oraz przygotowane aktualizacje, (3) wyłączenie niegotowych endpointów poza scope i serwerowe auth/zgody/quota, (4) testy dwóch kont, walidacji, odwołania zgód, signed URL i awarii providerów w stagingu z mockami, (5) niezależne retesty. Żadnego high/critical w zakresie nie zamyka się na podstawie nowego dokumentu lub pojedynczego testu buildu.
